# 1. Анализ архитектурных подходов

## Вариант 1: Go-бинарник (встроенный HTTP-сервер, FSM со стейт-файлом `state.json`, cross-platform)

**Архитектурный паттерн и рантайм**

- Монолитный статически скомпонованный Go-бинарник (`CGO_ENABLED=0`), внутри — четыре подсистемы: `serial` (COM-порты), `expect` (движок ожидания промптов), `httpd` (встроенный `net/http` для отдачи образов ONTAP), `fsm` (конечный автомат с персистентным `state.json`).
- Windows air-gap (RDP): копируется `ontap-auto.exe` + папка `images/` + `config.yaml`. Никаких зависимостей, никакого Python, никакого внешнего nginx.
- Linux air-gap: тот же бинарник, собранный под `linux/amd64`, запускается как systemd-юнит или напрямую.
- Конфиг `config.yaml`: COM-порты A/B, IP/маска/шлюз для e0M, URL образа, целевые версии, имена узлов, cluster-IP.

**Оркестрация ступенчатой прошивки HA-пары**

- FSM содержит раздельные ветки `nodeA` и `nodeB`. Каждая ветка — явный граф состояний: `loader` → `boot menu → пункт 7 (e0M, IP, маска, шлюз, HTTP URL) → ожидание загрузки ONTAP → CLI`.
- Переход между ветками жёсткий: нода A проходит полный цикл до CLI, затем FSM переключается на ноду B. Параллельная прошивка исключена архитектурно.
- `state.json` хранит `{current_node, step, last_prompt_seen, version, in_flight}`. Разрушительные шаги (`wipeconfig`, `9a`, `9b`, `cluster create`) помечаются `in_flight=true` до отправки и снимаются после подтверждения результата.

**Поведение при аварийном завершении процесса**

- `state.json` пишется атомарно (`write tmp → fsync → rename`) на каждом переходе FSM.
- При перезапуске бинарник читает стейт, переоткрывает COM-порты и **пассивно читает** текущий вывод консоли, чтобы определить фактическое состояние (Loader / Boot Menu / ONTAP CLI / загрузка).
- Если фактическое состояние совпадает с сохранённым шагом — продолжает с него. Если нет — FSM пересчитывает шаг по распознанному промпту и продолжает с корректной точки.
- При `in_flight=true` FSM не повторяет разрушительную команду, а переходит в режим диагностики и ждёт оператора.

**Главная точка отказа (SPOF)**

- Единственный экземпляр бинарника на jump-хосте. При отказе ОС, питания или COM-портов обе ноды остаются в неопределённом состоянии загрузчика; восстановление требует ручного вмешательства (хотя `state.json` позволяет корректно продолжить после подъёма хоста).

## Вариант 2: Python standalone (внешний HTTP-сервер, линейный пайплайн с блокирующими вызовами)

**Архитектурный паттерн и рантайм**

- Python-приложение, упакованное в один исполняемый файл: Windows — `pyinstaller --onefile` → `ontap-auto.exe`; Linux — `shiv`/`pex`/`zipapp` → `ontap-auto.pyz` или PyInstaller-бинарник.
- Внутри — `pyserial` для COM, `requests`/`http.server` для HTTP, линейная последовательность блокирующих вызовов, `json` для стейта.
- Внешний HTTP-сервер: `python -m http.server` (или `nginx`/`caddy` в air-gap-поставке) отдаёт папку `images/`. Утилита поднимает его как дочерний процесс и следит за жизненным циклом.
- Windows air-gap (RDP): exe + папка `images/` + внешний HTTP-процесс. Риск зависимостей PyInstaller (антивирус, VC++ runtime, различия в путях).
- Linux air-gap: zipapp/PyInstaller + внешний HTTP-процесс.

**Оркестрация ступенчатой прошивки HA-пары**

- Жёсткая линейная последовательность: полная прошивка ноды A (Loader → Boot Menu → пункт 7 → ожидание ONTAP → CLI), затем полная прошивка ноды B.
- Блокирующие вызовы читают вывод COM-порта до появления ожидаемого маркера. Повторные попытки реализованы через исключения и циклы `while` с таймаутом.
- Очередь шагов сериализуется в `state.json` (`{queue: [...], current: {...}, done: [...]}`) после каждого шага.

**Поведение при аварийном завершении процесса**

- При старте утилита читает `state.json`, восстанавливает очередь, отбрасывает уже выполненные шаги, переоткрывает COM-порты и продолжает с первого невыполненного.
- Разрушительные шаги помечаются `in_flight` до отправки и снимаются после подтверждения.
- Ограничение: очередь линейная, поэтому при несовпадении фактического состояния консоли с ожидаемым шагом утилита останавливается и требует ручного вмешательства (нет FSM-пересчёта по распознанному промпту).

**Главная точка отказа (SPOF)**

- Единственный Python-процесс на jump-хосте плюс зависимость от корректной работы дочернего HTTP-процесса. При падении — неопределённое состояние нод и необходимость ручного восстановления всей последовательности.

## Вариант 3: Двухфазный агент (Фаза 1: COM/Expect до поднятия сети → Фаза 2: SSH/API)

**Архитектурный паттерн и рантайм**

- Один процесс, две фазы:
  - **Фаза 1 (COM/Expect)**: управление COM-портами до момента, когда ONTAP поднял сеть и доступен по SSH. Включает: вход в Loader, Boot Menu → пункт 7, заливку образа по HTTP, ожидание загрузки ONTAP, ожидание CLI prompt.
  - **Фаза 2 (SSH/API)**: после получения IP — подключение по SSH (`golang.org/x/crypto/ssh` или `paramiko`), выполнение команд ONTAP CLI: `cluster create` (только на LOADER-A), настройка SP (`system service-processor network modify`), создание management LIF на e0M, маршруты.
- Windows air-gap (RDP): бинарник + папка `images/` + встроенный HTTP-сервер (как в Варианте 1). Требует COM-драйверов и SSH-клиента.
- Linux air-gap: тот же бинарник.
- Порядок фаз жёстко задан `docs/inputs.md`: сначала `cluster create` на LOADER-A, затем SP и e0M; Controller-B присоединяется автоматически.

**Оркестрация ступенчатой прошивки HA-пары**

- Нода A: Фаза 1 (COM) → образ через пункт 7 → ожидание IP → Фаза 2 (SSH). После успешного поднятия ONTAP на ноде A агент подключается к COM-порту ноды B и повторяет процедуру.
- Переключение между фазами и нодами управляется из единого процесса. Параллельная прошивка исключена архитектурно.

**Поведение при аварийном завершении процесса**

- Стейт-файл `state.json` хранит `{phase, node, step, ssh_session_hint, in_flight}`.
- Фаза 1: при перезапуске — переоткрытие COM, пассивное чтение, распознавание фактического состояния (Loader / Boot Menu / ONTAP CLI), продолжение с корректного шага.
- Фаза 2: при перезапуске — переподключение по SSH к уже поднятой ноде, проверка фактического состояния (`cluster show`, `network interface show`, `system service-processor network show`), продолжение с первого невыполненного шага. Команды идемпотентны на уровне проверки состояния перед выполнением.
- Разрушительные шаги (`cluster create`) помечаются `in_flight` до отправки и снимаются после подтверждения.

**Главная точка отказа (SPOF)**

- Jump-хост с COM-портами как единственная точка входа на этапе загрузчика. После перехода на SSH отказ jump-хоста менее критичен, но для CLI-этапов всё равно нужен доступ. Дополнительный риск — переход Фаза 1 → Фаза 2 зависит от того, что ONTAP действительно поднял сеть и SSH-доступ; при проблемах с сетью (link-local `169.254.x.x`, отсутствие маршрута) Фаза 2 не стартует.

## Сводная таблица компромиссов (Trade-off Matrix)

| Критерий | Вариант 1 (Go FSM) | Вариант 2 (Python Standalone) | Вариант 3 (Двухфазный агент) |
|---|---|---|---|
| **Автономность** | Высокая — один бинарник + `images/`, без зависимостей | Средняя — PyInstaller + внешний HTTP-процесс | Высокая — один бинарник + `images/`, но нужны COM-драйверы и SSH-клиент |
| **Надёжность прошивки** | Высокая — FSM, `state.json`, явные переходы, пересчёт шага по промпту | Средняя — линейная очередь + `state.json`, без пересчёта по промпту | Высокая — `state.json` на обеих фазах, идемпотентные проверки перед командами |
| **Сложность отладки** | Средняя — чтение `state.json` и логов FSM | Низкая — линейный вывод, простая трассировка | Высокая — две фазы, два протокола (COM и SSH) |
| **Риск окирпичивания** | Низкий — `state.json` + `in_flight` позволяют перезапуск с прерванного шага без повтора разрушительных команд | Средний — линейная очередь останавливается при несовпадении состояния, требуется ручной разбор | Средний — Фаза 1 восстанавливается по промпту, Фаза 2 зависит от SSH-доступности; при сбое сети утилита остаётся в Фазе 1 |
